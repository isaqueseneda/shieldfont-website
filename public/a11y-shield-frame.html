The enclosing frame

The shape is the box: an outline that encloses the notice strip and the text together. That is the invariant across all ten — they differ in how the outline is drawn and how the strip is composed, never in whether the text is inside it.

Every box below holds a whole document, not a paragraph: heading, prose, a quote, a list, and a bold phrase, all from one Markdown string. Switch the rail to format="text" to see the single-paragraph default.

Markdown fits without weakening anything. <Shield> rejects nested JSX on purpose — it cannot see inside your components, so their text would ship unencoded inside a block that still looks protected. Markdown is still one string, so that invariant is untouched.
Correction to what this file said an hour ago. I claimed the whole document encodes in a single encode() pass. That is true only for the subset this demo uses. Structural punctuation does survive — WORD_RE is /\p{L}+/gu — but a single pass rewrites URLs (https, example and path are all dictionary words), permutes digits, and renames HTML attributes. The sharpest one: 10. becomes 15., because 0→5 — so every ordered list silently renumbers. The correct order is parse the original → encode each text leaf → build elements, which is what html.ts already does. The demo document below avoids every broken construct, which is precisely why the shortcut looked sufficient.

Notes

Why the box matters

A strip floating above loose paragraphs says “here is a notice.” A strip on the top edge of a box that contains the text says “everything in here behaves differently, and this is the control for it.” The second needs no explaining, and it is the only version where the failure state has somewhere to go — the outline itself turns amber, so the thing that changes colour is the thing enclosing the bad text.

What format="markdown" actually costs

The supported grammar is deliberately small, and everything outside it throws at build time rather than degrading: headings ##–######, paragraphs, one level of blockquote, one level of unordered list, **strong**, *em*, inline `code`. Rejected, each for a reason:

  • Links and images — the URL cannot be encoded (it breaks) and cannot be left in clear (it leaks). There is also no version where this is accessible: a focusable <a> inside an aria-hidden subtree is a WCAG failure every audit tool flags, and it cannot be fixed without un-hiding the decoy.
  • Ordered lists — the marker is structural, so 10. encodes to 15.. Worse, the browser generates the numeral itself and renders it through the shielded font, so it would be permuted on screen too.
  • Raw HTML — rejected, not sanitised. A sanitiser is a permanent attack surface for a feature nobody asked for, and any surviving tag carries unencoded attribute names into a block that still looks protected.
  • Code fences — monospace matters most exactly where Optik’s coverage of {}, => and | is least verified.

I was too optimistic about one thing earlier. A heading inside the protected region does not appear in heading navigation, because aria-hidden="true" hides all descendants — so the structural win before reveal is only a correct DOM outline for CSS, print, selection and reading order. The real win lands after reveal: the revealed output is clipped with clip-path, never display:none, so its headings are in the accessibility tree and do participate in the outline. That is the first time a shielded article contributes anything to heading navigation.

One seal for the document, not one per paragraph

The box has one strip, so it makes one promise and runs one grind. Sealing per paragraph would mean N moduli and N ciphertexts in the HTML for a single control, and a reader pressing one button would still wait for the slowest of them. The whole document is sealed as one Markdown string and rendered twice — decoy now, original after.
